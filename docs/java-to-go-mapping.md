# Java 到 Go 的迁移映射

这份文档不是语法对照表，而是帮助你减少错误迁移习惯。

## 总原则

从 Java 转 Go，最大的难点通常不是语法，而是思维模型切换。

Java 常见倾向：

- 先设计完整抽象
- 类和层次结构驱动代码组织
- 依赖异常机制表达错误
- 倾向框架先行

Go 常见倾向：

- 先写清晰直接的代码
- 组合优先于继承
- 显式返回错误
- 标准库优先，小步演进

## 核心概念映射

| Java | Go | 迁移时要注意什么 |
| --- | --- | --- |
| class | struct + function/method | Go 没有类继承，数据和行为可以组合，但不要强行模拟 OOP 层次 |
| interface | interface | Go 接口通常更小，强调行为最小化，不要定义过大的业务接口 |
| constructor | 工厂函数 | 一般用 `NewXxx()` 返回 struct 指针或值 |
| exception | error 返回值 | 错误是正常控制流的一部分，要主动处理，不要绕过 |
| inheritance | composition | 优先组合字段和能力，而不是设计继承树 |
| annotation | tag + 显式配置 | 反射可用但不要滥用 |
| thread pool | goroutine + channel / worker pool | goroutine 很轻量，但不是无限免费 |
| synchronized / Lock | sync.Mutex / RWMutex | 仍然需要严格控制共享状态 |
| CompletableFuture | goroutine + channel + context | Go 更强调简单并发原语组合 |
| Maven/Gradle | go mod | 依赖和构建链路更轻 |
| Spring Boot 自动装配 | 手动组装依赖 | Go 更常见显式 wiring，代码更直白 |

## 最容易带过来的 Java 误区

### 1. 过早抽象

Java 经验容易让你先写很多 interface、service、impl、factory。

在 Go 里，如果只有一个实现，先不要急着抽象。先把代码写清楚，等真实变化出现再抽象。

### 2. 想用异常思路处理错误

Go 中错误不是异常替代品，而是函数签名的一部分。你需要把错误路径写清楚。

错误处理的关键不是少写几行，而是：

- 出错时能定位
- 调用方能决定怎么处理
- 错误信息有上下文

### 3. 习惯“万物对象化”

Go 可以写 method，但不代表每段逻辑都要挂在某个类型上。

很多场景下，简单函数比人为造对象更清晰。

### 4. 忽略值语义和指针语义差异

Java 几乎总是引用语义思维。Go 里值拷贝非常常见。

你要清楚：

- 什么时候传值更安全
- 什么时候需要指针避免拷贝或修改原对象
- slice、map、channel 虽然是值传递，但内部行为与普通 struct 不一样

### 5. 默认追求框架化开发

Go 生态里很多服务直接基于标准库或小型框架即可。学习初期不建议先依赖复杂框架，否则容易把重点放错。

## 面向求职的迁移重点

你不需要把 Java 经验“清空重练”，而是要把已有优势迁移过来：

- HTTP API 设计经验
- 数据库和事务经验
- 日志、监控、排障意识
- 分层与可维护性意识
- 线上问题定位思维

你需要重点补的是：

- Go 语言本身的表达方式
- Go 的并发模型
- Go 项目常见工程组织方式
- Go 面试中的常见语言细节

## 一句判断自己是否真的在转变

当你开始少问“Go 里怎么实现 Java 那套”，多问“这个问题用 Go 最自然的写法是什么”，说明迁移开始有效了。
