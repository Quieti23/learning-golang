# 常见坑

这份清单优先记录 Java 后端转 Go 早期最容易踩的坑。

## 1. 把 Go 写成简化版 Java

表现：

- 先设计很多层和很多 interface
- 一个简单功能拆出过多文件和抽象
- 过早引入复杂框架

修正：

- 先写直接、清晰、可运行的代码
- 没有变化点就不要先抽象
- 先用标准库把主线跑通

## 2. 错误处理偷懒

表现：

- 到处 `_` 忽略错误
- 只打印错误，不返回上下文
- 用 panic 代替正常错误处理

修正：

- 每个错误都问自己：调用方应该怎么知道失败了
- 用 `fmt.Errorf(... %w ...)` 包装上下文
- panic 只留给真正不可恢复的问题

## 3. 对指针和值语义没有感觉

表现：

- 不知道什么时候该传指针
- 修改 struct 后发现外部没变
- 不清楚 slice 和 map 的行为

修正：

- 主动做小 demo 验证值拷贝和引用效果
- 遇到不确定的情况，先写最小实验再下结论

## 4. 误解 interface 的用途

表现：

- 一开始就定义大接口
- 为了“面向接口编程”而写接口
- 只有一个实现也强行抽象

修正：

- 先写具体类型
- 只有当调用方真的需要抽象时，再定义小接口
- 接口放在使用方附近，而不是实现方先定义一堆

## 5. 过早接入数据库和框架

表现：

- 语言还不熟就开始 gin、gorm、redis、docker 全套
- 项目复杂度高于当前学习阶段

修正：

- 第 1 个月先用标准库和内存存储
- 先把 HTTP、JSON、错误处理、测试做稳

## 6. 没有测试意识

表现：

- 写完能跑就结束
- 不知道怎么验证边界输入
- 改一处坏一片

修正：

- 从 table-driven tests 开始
- 优先测试纯逻辑和 handler 的关键路径
- 每次补一个边界条件测试

## 7. 用看懂代替会写

表现：

- 看示例觉得简单，自己写就卡住
- 复盘时发现大部分内容离开参考资料就写不出

修正：

- 学完一个点，立刻空手重写最小示例
- 不要把“能看懂”当作完成标准

## 8. 卡在细节上导致主线停滞

表现：

- 为一个语法点查太久
- 为目录结构反复纠结
- 学习节奏频繁中断

修正：

- 主线优先，细节做记录后再补
- 只做当前阶段最需要的结构设计
- 先完成最小闭环，再优化

## 9. 不复盘，导致重复踩坑

表现：

- 同样的问题一周内反复出现
- 不知道自己到底进步了什么

修正：

- 每周固定复盘一次
- 把错误模式写下来，而不是只记结论

## 10. 只学语言，不学后端场景

表现：

- 语法练了很多，但不会做服务
- 知识点之间没有业务连接

修正：

- 从第 1 个月开始就围绕 HTTP API 项目学习
- 每学一个点，都问自己它在后端服务里怎么用

## 使用建议

当你再次踩到同一个坑，不要只修代码，把坑补到这份文档里，并写一句“下次如何更早发现”。这样这份清单才会越来越有用。
