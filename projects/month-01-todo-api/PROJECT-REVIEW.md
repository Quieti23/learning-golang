# month-01-todo-api 项目复盘

## 1. 项目目标是什么

- 用 Go 标准库从零做一个最小可运行的 Todo API。
- 把第 1 个月学到的基础能力串起来，包括 HTTP、JSON、错误处理、分层结构和基础测试。
- 先做出一个可运行、可讲清、可继续扩展的内存版后端项目，而不是一开始追数据库和复杂框架。

## 2. 实现了哪些功能

- 已实现最小 CRUD：
  - `POST /tasks`
  - `GET /tasks`
  - `GET /tasks/{id}`
  - `PUT /tasks/{id}`
  - `DELETE /tasks/{id}`
- 已实现统一 JSON 错误返回。
- 已实现基础参数校验：
  - 非法 JSON
  - 空请求体
  - 空标题
  - 非法任务 ID
- 已补最小测试：
  - `service` 层 table-driven tests
  - `handler` 层关键 HTTP 路径测试

## 3. 用到了哪些 Go 能力

- 标准库 `net/http` 写最小 HTTP 服务。
- `encoding/json` 处理请求和响应。
- 显式错误返回和错误分支处理。
- `struct` 和 `json` tag 定义接口数据结构。
- `slice` 做内存存储。
- `sync.RWMutex` 保护共享内存。
- table-driven tests。
- `httptest` 做基础 HTTP handler 测试。
- 分层组织代码：`handler -> service -> store -> model`。

## 4. 遇到的主要问题

- 一开始容易把逻辑都堆进 handler，分层边界不稳定。
- 导入路径、模块名、包结构在刚开始搭骨架时容易出错。
- `go test ./...` 通过并不代表有测试，只可能是“没有测试文件”。
- HTTP 路由和 method 设计一开始有些重复，后来才收敛到 `/tasks` 和 `/tasks/{id}`。
- JSON body 解析如果不收紧，空 body、未知字段、多对象 body 容易悄悄通过。

## 5. 关键设计取舍

- 为什么这样划分包和结构：
  选了最小分层：`handler` 负责 HTTP，`service` 负责业务规则，`store` 负责内存数据访问，`model` 只负责数据定义。这样足够清楚，也不会一开始过度设计。

- 为什么这样处理错误：
  先统一成最简单的 JSON 错误结构：`{"message":"..."}`。这样能先把接口行为稳定下来，让成功和失败路径一致，方便调试和测试。

- 为什么这样定义接口或不定义接口：
  目前没有提前引入 interface 抽象，`service` 直接依赖具体 `store`。这是刻意保持简单，因为第 1 个月的重点是把功能和分层做扎实，不是提早抽象。

- 为什么先用内存存储：
  当前阶段的目标是掌握 Go HTTP 服务和工程基本盘，不是数据库接入。内存存储让 CRUD、错误处理和测试可以更快推进，不会被环境问题打断主线。

## 6. 如果重做一遍，我会怎么改

- 更早统一路由风格，直接使用 `/tasks` 和 `/tasks/{id}`，避免中途出现重复路径设计。
- 更早把错误写法统一成 helper，减少 handler 里重复的状态码和错误映射代码。
- 更早补关键路径测试，而不是等 CRUD 基本完成后再补。
- `store` 一开始就用 `RWMutex` 区分读写，而不是后面再调整。
- README 可以更早补充示例请求，方便手动验收和回归检查。

## 7. 当前结论

这个项目已经达到“第 1 个月可展示的最小成果”标准：

- 可运行：是
- 可说明：是
- 可修改：是
- 可继续扩展：是

但它还明显是“第 1 个月项目”，不是完成版工程。当前最主要的不足是：

- 没有数据库
- 没有更完整的测试覆盖
- 没有更细的错误码体系
- 没有配置管理和日志体系
- 路由和 HTTP 层仍然是标准库最小写法，工程化程度有限

## 8. 一句话总结

这个 Todo API 的价值不在于功能复杂，而在于已经把 Go 后端最基础的一条线跑通了：定义数据、处理 HTTP、组织分层、返回 JSON、做基础测试，并且能解释为什么这样组织。
